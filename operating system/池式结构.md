# 1. 什么是线程池

本质上是一个池式结构, 可以复用线程这个资源, 不需要每一次使用时创建, 用完后销毁

# 2. 线程池解决什么问题

1. 执行异步的耗时任务
2. 充分的利用多核优势

# 3. 线程池如何解决问题的

线程池本质上就是一个生产者消费者模型, 一般流程是, 生产者线程抛出一个耗时任务到队列中, 然后唤醒一个消费线程去队列执行这个任务, 当队列为空时会阻塞消费者线程。线程池的核心是队列的设计, 会根据生产者的数量以及使用场景去设计不同的队列, 比如说skynet下, 是每一个actor都有一个队列 组成的二级队列, 比如说workflow框架中的三个线程池, 可能又是不一样的设计

# 4. 线程池中线程数量的确定

这里分为两种情况的经验:
1. CPU密集型的任务: 是耗时计算, 不会有频繁的用户态内核态切换, **经验: CPU核心数的线程数量**
2. IO密集型的任务: 是耗时等待, 会有频繁的用户态内核态切换, **经验: CPU核心数×2的线程数量**

实践中以线程池的吞吐量来决定线程数量选择(单位时间内, 执行任务的个数)

# 5. 线程池的实现

![[ed2e39cf-4d1c-4537-8d56-f0f0c78a06c5.png]]
condition_variable::wait 函数的用法有两种
```c++
// 方式A：手动while循环 
while (!ready) { cv.wait(lock); } 

// 方式B：传入谓词（推荐，更简洁） 
cv.wait(lock, [](){ return ready; });

//第二种写法等价于:
while (!pred()) { cv.wait(lock); }
```

![[92228ddd-e189-4f1a-b501-72b3adec1b12.png]]


执行流程:
以 `cv.wait(lock, pred)` 分步拆解：
1. **先判断 `pred()`**
- 如果 `pred() == true`：**不阻塞，直接返回**，不释放锁；
- 如果 `pred() == false`：进入等待流程。
2. **释放传入的 unique_lock（解锁 mutex）**
3. 线程阻塞，等待被 `notify_one()` / `notify_all()` 唤醒
4. 收到通知后，**重新上锁**（获取 mutex）
5. 再次执行 `pred()`
- `pred() == true` → wait 返回；
- `pred() == false` → 再次释放锁、继续等待。

> 但是这里有一个值得讨论的点, 业务线程只负责把任务push到连接池即可, 连接池线程去拿到任务, 用本线程的TCP连接, 去MySQL查询数据, 问题是查询到数据后, 怎么把这个值返回给业务线程使用呢? 这是两个不同的线程, 并且这是一个异步的过程, 业务线程push了任务后, 就直接返回了, 不会等待连接池线程返回数据


需要使用到C++中的promise和future的用法:

它们是一对一次性的、跨线程的「值传递通道」，成对出现：
std::promise<T>: 写端：在某个线程里调用 promise.set_value(...) 往里塞一个值。
std::future<T>: 读端：另一个线程调用 future.get() 阻塞等待，直到值被塞进来，然后取走。
两者通过 promise.get_future() 绑定，本质是共享状态的一头一头。一个写、一个读

```c++
std::promise<int> p;
std::future<int> f = p.get_future();   // 绑定
// 线程A: p.set_value(42);             // 写
// 线程B: int v = f.get();             // 读（阻塞直到 A 写入）
```

最后连接池应该是这样使用这个特性的:
1. 每一个SQL任务中都有一个promise对象, 承诺每一次执行完SQL后都会给你返回一个ret结构体
```cpp
class SQLOperation {
    std::string sql_;
    std::promise<std::unique_ptr<sql::ResultSet>> promise_;  // 写端，随 op 一起被工作线程拿走
public:
    std::future<std::unique_ptr<sql::ResultSet>> GetFuture() {
        return promise_.get_future();                        // 派生出一个读端给业务线程
    }
};
```

2. 业务线程发起查询：拿到 future，把任务丢进队列
```cpp
QueryCallback MySQLConnPool::Query()
{
    if (!available_ || !task_queue_) {
        std::promise<std::unique_ptr<sql::ResultSet>> promise;
        promise.set_value(nullptr);                         // 异常路径：立即给个空结果
        return QueryCallback(promise.get_future(), std::move(cb));
    }
    auto op = std::make_unique<SQLOperation>(sql);
    auto future = op->GetFuture();                          // ① 拿到读端 future
    task_queue_->Push(std::move(op));                       // ② 把写端（op）丢给工作线程
    return QueryCallback(std::move(future), std::move(cb)); // ③ 把 future+回调封装返回
}
```
future 留在业务线程手里（装在 QueryCallback 里）。promise（在 op 内）被 move 进任务队列，归工作线程所有。同一个共享状态，一头在工作线程，一头在业务线程

3. 工作线程从队列取出 op，执行查询后调用 promise_.set_value(...)，这一刻共享状态被填满，业务线程的 future 就从「未就绪」变「就绪」
```cpp
void SQLOperation::Execute(MySQLConn *conn)
{
    auto result = conn->Query(sql_);                        // 真正执行 SQL
    promise_.set_value(std::unique_ptr<sql::ResultSet>(result));  // 写入结果，future 立刻就绪
}
```

4. 业务线程轮询 future，就绪就回调, wait_for(seconds(0)) 是「非阻塞探测」：立即返回当前状态。main.cpp:48-52 的循环每 100ms 调一次 response_handler.InvokeIfReady()，把所有就绪的回调跑掉，不就绪的留到下一轮
```cpp
bool InvokeIfReady() {
    if (future_.wait_for(std::chrono::seconds(0)) == std::future_status::ready) {
        cb_(std::move(future_.get()));                      // 取出结果，调用业务回调
        return true;
    }
    return false;
}
```

C++项目一般规则: 
1. .hpp声明class, 使用指针/引用, .cpp才include头文件, 减少头文件依赖
2. 要初始化一个类中的成员变量或者初始化一个类型时, 先定义一个局部变量, 把所有可能初始化失败的情况都判断后, 再直接使用move, 把这个局部变量的值移动到成员变量上
